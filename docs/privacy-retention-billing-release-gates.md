# Hoopzaro — privacy, retention and billing release gates (draft)
2026-11-26. This is an engineering checklist, not a legal opinion. Keep the existing admin pilot; keep customer analytics and live billing disabled.

## Privacy: current facts and launch gates
- The public application runs on Streamlit with Google OIDC. The dedicated Control Center uses separate deployment secrets; do not change the working OAuth client or auth cookie.
- Analytics reads on Control Center are aggregated. The application stores no raw analytics query, email or IP in the telemetry tables. Hosting logs and other providers may still process personal data. Pseudonymous records are not necessarily anonymous.
- Session opt-in currently resides in memory. Before launch, implement durable, minimal evidence of affirmative action, notice version, time, purpose and withdrawal. An opt-in write must succeed before collection begins. Withdrawal must stop collection even if the audit write fails; do not restore consent after a browser reload or account switch.
- Proposed evidence design: separate session-consent grant UUID (link to telemetry session only) and account-consent receipt keyed to the HMAC account identifier, with no direct session/account join. Store notice version, accepted UTC and withdrawn UTC. Keep no raw claims or IP. Use server-derived identities and fixed purpose/notice IDs. Proof failure -> do not grant; withdrawal failure -> stop locally, mark a sanitized error, no resumption. Add explicit deployment gate for approved notice and evidence schema. Test duplicate clicks, no consent, identity switch, role transition, unavailable DB, withdrawal and expired grants.
- Define proof retention and separate account observation from operational quota records before deletion can become automatic. Keep proof for as long as needed to demonstrate processing; have counsel approve deletion criteria. Verify data subject access/erasure handling when sessions cannot be linked to accounts. No additional tracking purely to identify users.
- Confirm legal controller name/address, DPO if applicable, actual recipients and processing agreements, international transfers, actual browser cookies/local storage, log/backup/support retention, age policy, applicable local laws. Contact and support addresses are already active. Do not commit private home address or secrets into a public repository. Legal review: GDPR Arts 5–7, 13–14, 15–22, 28, 32–34, 44–49; Polish PKE Art 399; launch markets beyond EEA need separate assessment.
- Publish final PL/EN notice with a reachable link from sign-in, Settings before consent and payment flow. No draft placeholders on public UI. Ensure access without signing in and consistent language. Finalise terms of service and consumer subscription disclosures separately; privacy notice is not a contract or NBA licensing clearance.
- Verify consent evidence, no optional collection when disabled, withdrawal, guest/FREE/PREMIUM separation, and observed page batching on test accounts. Do not infer total registered people, true online count or actual page views from consent samples. Document prior controlled pilot processing and handling of existing records.

## Retention: staged activation
Already on main: analytics_retention.py and .github/workflows/analytics-retention.yml. Workflow is disabled unless repository variable HOOPZARO_RETENTION_ENABLED is exactly true. APPLY is a separate switch. Uses a transaction, database name guard, fixed SQL and timeouts. A direct read-only query has found zero eligible rows in the current database; this is not a scheduled execution or deletion.
1. Inspect GitHub repository Settings > Secrets and variables > Actions. Configure repository secret HOOPZARO_RETENTION_DATABASE_URL using a Neon connection to hoopzaro_analytics, initially the read-only hz_analytics_reader role. Copy directly from Neon into GitHub, never send it in chat, commit or logs. Leave other DB URLs and tracker secrets intact.
2. Set repository variable HOOPZARO_RETENTION_ENABLED=true and HOOPZARO_RETENTION_APPLY=false. Run Analytics retention manually via workflow_dispatch on main. Verify counts and no data changes. Schedule is 03:17 UTC daily (04:17 CET / 05:17 CEST); GitHub may delay runs.
3. Before apply, approve exact deletion scope and check restore capability/backup retention. Provision a dedicated narrow role; it must not have access to tracker, payment, admin audit or delete quota. Prefer a narrowly reviewed server-side cleanup function or restricted service role with only the needed permissions, account parent-row lock permissions included. Do not reuse the application writer or owner credentials. Verify dry-run and transaction rollback on test branch using fixture rows before changing the secret.
4. Only after explicit approval, switch to the dedicated role and set HOOPZARO_RETENTION_APPLY=true. Review first run, job logs (counts only) and monitoring; revert APPLY=false or ENABLED=false if anything unexpected. No destructive SQL to be run on production during preparation.
5. Current retention implementation: 30 UTC calendar-day window for page samples, 30 days since last seen for sessions (retains linked unexpired samples); 90 UTC calendar-day window for feature aggregates; inactive accounts 90 days with quota-dependent rows excluded. Backup copies and any consent receipt tables require a separately documented policy. Jobs must never delete quota records by cascading foreign keys. Retention for accounts is not Google deletion or cancellation of subscription.

## Billing: test first, separate trust boundary
Current state: Control Center read-only sandbox reporting works. The public app uses a static test Payment Link and server-side OIDC allowlists; link success does not grant Premium. Leave live checkout disabled. Do not use Control Center restricted read key for Checkout creation; use a separate test-only key limited to required capabilities. No production financial key or webhook secret goes to the browser.

Proposed architecture:
- Public Streamlit app verifies OIDC and creates an opaque random checkout attempt on server. Account mapping uses a new billing HMAC key (separate from optional analytics), immutable issuer + subject. Never use checkout email or browser-supplied identity to determine entitlement. Consent to analytics not required for billing.
- Create Stripe Checkout Session on the server with mode=subscription, known test Price ID, quantity 1, configured USD 9.99/month, approved return URLs, idempotency key; save server-owned attempt/session mapping. Validate configured Price via Stripe API (test/live flag, monthly recurring, unit amount, currency and product); no user-provided price or redirect. Opaque attempt ID, not OIDC claim, may be sent as client_reference_id. Persist unique mapping of Stripe customer/subscription to account. Avoid duplicate active subscriptions and handle abandoned attempts. Validate checkout URL before exposing it.
- Independent HTTPS webhook receiver: choose supported hosting runtime before deployment; Streamlit Cloud frontend is not a generic webhook receiver. Verify raw request bytes and Stripe-Signature using official Stripe SDK, endpoint-specific secret, clock tolerance, correct sandbox/account and bounded body size. Do not accept forged success URLs, manual email matching or client event payloads. Persist unique event ID with processing state; return success only after durable acceptance; retry failures. Handle out-of-order events by reconciling fresh Stripe state and serialising updates per subscription, not granting access based on event order. Pin supported API version and test adapter against actual sandbox payloads.
- Relevant events: checkout.session.completed / async_payment_succeeded / async_payment_failed, invoice.paid / invoice.payment_failed, customer.subscription.created / updated / deleted and appropriate refund/dispute events. Webhook is a signal: retrieve canonical subscription and invoice/payment state from Stripe; verify known Checkout mapping, customer, product/price, environment, paid invoice line and paid-through period; refund/dispute policy must be decided and tested. No premium on incomplete, unpaid, wrong product, wrong account, revoked or unknown state. Default proposed sandbox access only active status and valid paid period; no trial/grace until explicitly approved. Cancellation at period end while active remains allowed only through confirmed paid period.
- Persist minimal billing records in a separate test data store, not analytics/quota tables. Unique constraints for Stripe event ID, checkout session ID, customer mapping, subscription mapping. Store reference identifiers, status, verified paid-through timestamp, verification timestamp, environment and reason codes; do not store card details, raw payloads or email in entitlement table. Separate reader role for app, writer role for webhook/backend. Define retention and legal obligations before real payments.
- Access control: existing ADMIN precedence unchanged. Server-side grant lookup for signed-in OIDC principal, fail closed for missing/stale/mismatched billing evidence; existing manual Premium allowlist retained during testing. Test entitlement restricted to designated sandbox testers and isolated instance/explicit flag, never enable for production customers on a test payment. Cache only narrowly per principal and expiry; handle downgrade by invalidating cached Premium outputs. Kill switch disables new automated grants but preserves existing admin/manual access.
- End-to-end verification: free user initiates checkout; correct test product; Stripe test card; authenticated return; webhook signature verified; payment confirmed; account A gets Premium only in isolated test; account B stays FREE; duplicate/replayed event safe; canceled, failed, refunded, disputed, expired, out-of-order, unavailable API/DB, wrong currency/price/account/live event and forged URL do not grant. No charging real cards. Confirm support/admin can diagnose without disclosing identifiers or secrets.
- Before production: controller/business/legal details, consumer terms, cancellation/refunds, VAT/invoices, market rules, tax/Stripe account verification, NBA data licensing, vendor DPAs, monitoring and operational incident response. Production separate from sandbox, with separate keys, Price IDs, DB, endpoint secret and event scope. No activation until signed-off end-to-end tests.
