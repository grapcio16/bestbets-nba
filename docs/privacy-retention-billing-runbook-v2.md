# HOOPZARO release runbook — privacy, retention and billing sandbox v2
2026-11-26. This branch adds isolated billing code, draft notices and a bounded retention function. None of the changes enables customer telemetry or real payments. It supersedes PR #195, whose old base could not be merged. Durable consent was already merged in PR #196.

## 1. Privacy release blockers
PL/EN drafts in docs/privacy-policy-*.draft.md v0.2. Verify actual controller name/contact address, mailbox ownership, subprocessors, DPA and regions, cookies, log/backup/support retention, consent-receipt retention, age and target markets. Do not publish a draft or commit private personal details without approval. GDPR arts. 7 and 13: demonstrate consent and provide controller and processing information. Poland PKE art. 399: verify storage/access on user devices.
Code now stores separate receipts and bounds consent at 24 hours; after DB failure withdrawal stops collection but its proof may not persist if session closes before retry. No collection before a durable committed receipt. Keep HOOPZARO_USAGE_CUSTOMER_ENABLED=false and HOOPZARO_USAGE_CONSENT_READY=false until all gates are satisfied. Do not alter [auth]. Publish approved immutable notice on own domain and set actual URL/version (2026-11-26-v2); check link in browser before switching on. Do not claim general GDPR compliance solely from tests. Receipt retention needs a documented separate rule and request-handling procedure.

## 2. Retention: read-only scheduled pilot
The existing workflow on main already accepts workflow_dispatch and runs daily 03:17 UTC. GitHub connector cannot set repository Secrets/Variables. The user must do this in GitHub Settings > Secrets and variables > Actions:
- Secret HOOPZARO_RETENTION_DATABASE_URL: copy Neon connection for the existing hz_analytics_reader role and hoopzaro_analytics database directly. Never paste into chat or git.
- Variables HOOPZARO_RETENTION_ENABLED=true and HOOPZARO_RETENTION_APPLY=false.
Then select Actions > Analytics retention > Run workflow > main. Review only aggregate counts. No data is deleted. Schedules may be delayed by GitHub. The test flag cannot activate payments or customer telemetry.
Do NOT set APPLY=true. This version changes apply to a dedicated HOOPZARO_RETENTION_EXECUTE_URL credential with SQL role hz_retention_runner and a fixed SECURITY DEFINER function; read-only role cannot execute it. Migrations/retention_runner_v2.sql is additive; do not run against Neon until reviewed/approved. Create a separate LOGIN role with no broad schema/table privileges; verify inherited grants and default privileges, then grant only schema USAGE and function EXECUTE. Never use owner or general writer in Actions. Check actual database name, current role, backup/restore, test transaction, role grants and expected counts. Apply only after explicit authorization of exact targets. Function bounds deletions at 5000 per category per invocation, locks session/page tables to avoid orphans, and locks exact candidate accounts before rechecking the quota FK. It does not delete receipt records, audit, quota or billing. Dry-run counts are an upper estimate when capped or when an old session has leftover page rows; another run can clear remaining eligible records. Automatic deletion is not yet enabled. If lock timeout occurs, all changes roll back.
Consent receipt retention intentionally NOT automated; requires approved policy and data rights process. Keep database backups and restore copies in the review.

## 3. Sandbox billing — isolated checkout and verification
The public Streamlit app and access_control.py are untouched; manual admin/Premium behavior remains. Sandbox UI can be deployed as a separate private app from billing_sandbox_app.py with a separate Google OAuth callback for that app, not replacing the public OAuth client. Proposed host hoopzaro-billing-sandbox.streamlit.app must be reserved/verified; the code deliberately rejects any different return hostname. If unavailable, change the allowlist in code and retest before deployment.
- Create dedicated database hoopzaro_billing_sandbox (not analytics or tracker) and narrow roles hz_billing_sandbox_app / hz_billing_sandbox_webhook. Apply migrations/billing_sandbox_v1.sql there only. Check effective privileges; never share main DB writer.
- Use a new test-only restricted Stripe key with access to account, price, Checkout session creation/read, subscription/invoice/payment intent/charge read as needed. Do not reuse the existing Control Center read key. Verify exact Stripe account ID, active test product and Price $9.99 USD monthly. Stripe API version pinned to 2024-06-20 deliberately because the adapter uses the legacy invoice charge/payment_intent and line.price schema. Validate current sandbox API compatibility, including disabled adaptive pricing, before any rollout.
- Deployment-only variables: HOOPZARO_BILLING_SANDBOX_ENABLED=true (only private app), HOOPZARO_BILLING_SANDBOX_HMAC_KEY (32+ random bytes), HOOPZARO_BILLING_SANDBOX_ENROLL_EMAILS (comma separated verified test emails, only for initial pseudonym display), HOOPZARO_BILLING_SANDBOX_TESTERS (comma separated account HMAC values), HOOPZARO_BILLING_SANDBOX_STRIPE_KEY, HOOPZARO_BILLING_SANDBOX_STRIPE_ACCOUNT, HOOPZARO_BILLING_SANDBOX_PRICE_ID, HOOPZARO_BILLING_SANDBOX_PRODUCT_ID, HOOPZARO_BILLING_SANDBOX_RETURN_URL, HOOPZARO_BILLING_SANDBOX_DATABASE_URL. Generate credentials directly in providers; never send private values to chat. Test account hash is displayed only to explicitly allowlisted verified emails; it is an identifier, not an auth credential.
- Sandbox workflow: tester signs in with Google, uses server-created Checkout session, pays with Stripe test card, returns to app and presses Verify. On each decision the server retrieves canonical Checkout, subscription, invoice, PaymentIntent and charge, validates test mode/price/paid period/no refund/no dispute, persists binding. No grant on redirect, email, unknown or incomplete payment. Only card, one fixed monthly item, exactly 999 minor units USD, no discounts, taxes, credit notes, trial/grace, refunds/disputes. Cancel-at-period-end active paid subscription remains eligible until confirmed end. No repeated checkout for an existing account; after abandoned/uncertain checkout requires manual sandbox review, deliberately prevents duplicate charges. This narrow proof of concept is not a general billing system. Verified state is displayed in the sandbox only, never used by the production access gate.
- Independently deploy billing_sandbox_webhook:application behind HTTPS WSGI host with stripe SDK (tested version range stripe>=11,<13) and psycopg. POST /stripe/sandbox. Set HOOPZARO_BILLING_SANDBOX_WEBHOOK_ENABLED=true, HOOPZARO_BILLING_SANDBOX_WEBHOOK_SECRET (endpoint specific), HOOPZARO_BILLING_SANDBOX_STRIPE_ACCOUNT and HOOPZARO_BILLING_SANDBOX_WEBHOOK_DATABASE_URL (webhook only role). Register test endpoint with pinned API version 2024-06-20 and selected event types. Signature verification uses raw bytes and tolerance 300s; rejects live/invalid version; duplicate event id stored once. Stores id/type/time only, not raw payload. The webhook currently acts as durable audit inbox, not a reconciliation worker. On-demand verification is authoritative and does not depend on event arrival. For production event-driven fulfillment still needs durable worker, retry/reconciliation, cancellation/customer portal, multiple subscription lifecycle and failure policy, secure hosting, monitoring and full test matrix.
- End-to-end acceptance: correct test checkout + API confirmation, other identity remains FREE, failed payment, expired session, cancellation, wrong price, wrong account, wrong mode, refund/dispute, stale evidence, event replay, invalid signature, DB/API outage. Tests use fixture API and disposable DB; not equivalent to a real Stripe test payment. Do not enable real keys or real payments. Keep separate deployment entrypoint and DB, no changes to public [auth] or entitlement gate.
